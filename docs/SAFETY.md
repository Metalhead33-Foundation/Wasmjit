# Safety, Guardrails, and Known Pitfalls {#doc_safety}

Status: policy / implementation reference (revision 3 — adds the trap-cleanup
design pointer and records that a Go-style defer stack is a candidate, not
current behaviour; the guardrails themselves are unchanged).
Audience: anyone adding a feature to `WasmBase/` or a backend (currently
`LibJit/`), and anyone embedding the library in a process that must stay up.

This note is different from the `docs/proposals/` notes: it is not about a Wasm
proposal, it is about **not letting a module take the host down**. It records the
rules the engine follows, the pitfalls that were actually hit while building it,
and what is deliberately *not* guarded. It contains **no new code**.
For the separate question of guest-side versus host-side thread safety — and
which party is responsible for each — see [`THREADSAFETY.md`](THREADSAFETY.md).

## 1. Threat model (read this first)

- **A module is untrusted input.** It may be hostile, corrupt, or merely
  generated by a buggy tool. *Valid* Wasm is not the only input the loader sees:
  `Module::validate()` is a real rule set ([`VALIDATION.md`](VALIDATION.md)) but
  it is deliberately conservative — an unmodelled opcode taints the rest of the
  body instead of rejecting it (§3.1 S2) — so decoding and instantiation still
  have to survive bytes the validator let through.
- **The engine is not a sandbox.** There is no instruction budget, no watchdog
  and no memory isolation between a module and the host process. A module that
  loops forever will wedge the calling thread; the test harness handles that by
  running each script in a **forked child with a wall-clock timeout**
  (`Test/SpecSuite.cpp`), and an embedder that must survive hostile modules
  should do the same.
- **What we do promise:** a module cannot make the loader, the instantiator or
  the JIT allocate unbounded host memory, and every *runtime* failure surfaces as
  a Wasm trap or a C++ exception — never as `std::abort()`, a SIGSEGV or a hang.

## 2. Policies

### 2.1 Tell artifacts apart before decoding them

`Artifact::parse` (`WasmBase/WasmArtifact.cpp`) reads the preamble as magic (4) +
version (2) + **layer** (2) once and dispatches: layer 0 constructs a `Module`,
layer 1 a `Component`. `Module::fromFile` remains the core-only entry point and
rejects layer 1 with the component-specific message; `Component::fromFile`
requires layer 1 and version `0x0d`. Embedded core modules and nested components
inside a component are **full binaries with their own preambles**; the parser
reads each one through the same factory logic, with the enclosing section end as
a hard boundary.
*Encountered pitfall:* before CM-0 a component "loaded" as a nonsense module
([`proposals/COMPONENT_MODEL.md`](proposals/COMPONENT_MODEL.md) §4.1).

### 2.2 Never allocate on an input-derived size without a bound

Sizes in a module are LEB128 integers: **five bytes can claim four billion of
something.** Every such size is bounded, in one of two ways:

- **By the remaining input** — a length larger than the bytes left in the file is
  malformed *by definition*, so the check is exact and cannot reject a valid
  module. `WASM::requireAvailable` / `requireCountAvailable`
  (`WasmBase/WasmSafety.hpp`) implement it, and it is applied to names, function
  bodies, data segments and branch-hint counts (`WasmBase/WasmModule.cpp`) and to
  opcode list lengths in the body — `br_table`, `select_t`, catch clauses —
  (`WasmBase/WasmOpcodeDispatcher.cpp`, `readList`/`readListLEB128`).
- **By an explicit cap** — `kMaxFunctionLocals` (declared locals; one LEB can
  otherwise ask for hundreds of millions of JIT slots), `kMaxControlNesting`
  (nested blocks in one function), and for components
  `kMaxComponentSections` / `kMaxComponentNesting` (repeated sections and
  recursive nested components). Component section payloads are copied into a
  bounded buffer before decoding, so a malformed LEB cannot read into the next
  section; vector counts are checked against the remaining payload. Custom
  section names are bounded by the section, and the custom payload is retained
  at its input-derived size. Embedded core modules and nested components are
  parsed through their own preamble from a section-bounded buffer. Component
  index spaces and structural validation add one bounded entry per parsed
  definition; they do not allocate code, link, or mutate the `Store`.

### 2.3 Charge host memory against the store's budget

`WasmStore` is the single allocator for linear memory, tables and GC objects, and
it charges every byte against its **store's budget** *before* allocating (one
store per runtime, so one budget per runtime — there is no process-wide store):

- `createLinearMemory` / `createTable` (initial size), `growMemory` / `growTable`
  (deltas) and `allocateStructObject` / `allocateArrayObject` (GC heap);
- exceeding the budget is a **failed grow (`-1`)** for `memory.grow` /
  `table.grow` (the spec explicitly allows an implementation limit) and a
  **recoverable trap** for a GC allocation;
- an oversized *initial* size fails instantiation with a clear message.
- The **GC heap** is an mmap-backed region allocator owned by the Store
  (`WasmBase/WasmGcHeap.{hpp,cpp}`): regions are charged to the budget when they
  are backed and credited on instance teardown. It exists so that **running
  generated code never calls `malloc`/`calloc`/`free`** — allocation is a
  per-region free-list pop or a bump, and anonymous `mmap` provides the
  zero-filled memory `calloc` used to. See `proposals/GC.md` §6.1/GC-2.
- A continuation stack is charged to the same budget before it is created
  (`WasmContinuation.cpp`): A charges the mmap'd usable stack plus its guard
  page; B charges the pthread stack. The live-continuation count is separately
  bounded by `WASMJIT_MAX_CONTINUATIONS`, and the stack request by
  `WASMJIT_CONT_STACK_BYTES` (default 512 KiB). A refused `cont.new` or stack
  allocation is a recoverable `OutOfMemory` trap, never an allocation attempt.

Default budget **2 GiB**; override with `WASMJIT_MAX_TOTAL_BYTES` (bytes;
`0`/`unlimited` disables it, at your own risk). The whole test suite fits in
**64 MiB**, so the default is very generous.

**Encountered pitfall (the big one).** MEMORY64 widened
`memory.grow`/`table.grow` to 64-bit and — correctly — began treating the delta
as an *unsigned* index, but dropped the old signed-delta guard without adding
the spec's size limits. A single spec case,
`(table.grow (ref.null func) (i32.const 0xffffffff))`, then asked for ~34 GB
(`0xffffffff` pages is ~256 TiB for memory), and `std::vector::resize` zero-fills,
so the kernel handed out pages until the machine froze. See §4, case study 1.

### 2.4 A runtime failure is a trap or an exception — never `std::abort()`

- **Traps** are *reported*, not thrown across generated code
  (`WasmBase/WasmTrap.hpp`): the generated frames have no unwind tables, so a C++
  exception cannot cross them. Generated code, the JIT's `emitTrap` /
  `emitTrapIfNull` paths and the native helpers call `reportTrap()` (or, from
  generated code, `wasm_trap_report()`) and return a benign value; every caller
  checks the pending slot and returns in turn. The host boundary
  (`WASM::callCallable`, the start-function call, the test harness) converts the
  pending trap into a `WASM::Trap` C++ exception *after* the generated frames
  have returned, so ordinary C++ unwinding — and therefore ordinary destructors —
  applies to every C++ frame. The test harness converts the exception into its
  own trapped/kind/message result and *executes* `assert_trap`.
- Every trap carries a **kind** (`WASM::TrapKind`) as well as a message. The kind
  is the spec's taxonomy and `trapKindName` returns the spec's own wording, so the
  harness compares an `assert_trap` expectation against `trapKindName(kind)`:
  trapping for the *wrong* reason is a failure, not a silent pass. The message is
  free text for the log and may be finer-grained than the kind (e.g.
  "out of bounds memory.init source" for `OutOfBoundsMemoryAccess`).
  `TrapKind::Internal` means "this is not a spec trap" — a defensive index check,
  an unimplemented lowering — and must not be reachable in a conformant run.
- **Loader / instantiator / JIT problems** are `std::runtime_error` /
  `std::invalid_argument`, caught by the embedder. That includes an opcode the
  backend does not lower yet (`notImplemented`), a malformed export index, an
  out-of-range `memidx`, and a start-function index outside the index space.

A report never aborts by itself: with no C++ frame left to check it, the trap
simply remains pending until the boundary takes it. `WASM::trap()` is the
host-facing spelling (report + throw) and is only valid where no generated frame
is on the stack.

### 2.5 Locks and "regions" are RAII, not start/end pairs

LibJIT's build region is a **lock**: `jit_context_build_start()` must be paired
with `jit_context_build_end()`. An exception unwinding between the two skips the
unlock and the *next* `jit_context_build_start()` blocks forever — a **hang**,
not an error. `JitBuildScope` (`LibJit/LibjitModuleCompiler.cpp`) makes the pair
exception-safe. Any future "begin/end" API should get the same treatment.
*Encountered pitfall:* see §4, case study 2.

RAII is both exception-safe and trap-safe: a trap unwinds the engine's C++ frames
by returning, so `std::lock_guard`, `std::unique_ptr` and `std::string` are valid
across a trap-capable call. The one remaining rule is that a *helper called from
generated code* must report and return rather than throw (§2.6).

### 2.6 A helper called from generated code reports; it never throws or jumps

The generated frames have no unwind tables, so an exception leaving a helper
would have to unwind a frame the platform unwinder cannot describe. The contract
for every helper that generated code calls directly is therefore:

- a failure is `reportTrap(kind, detail)` followed by returning a benign value
  (`nullptr`, `0`, or a `bool`/status that the helper's caller checks);
- it must not call `WASM::trap()` (which throws), must not `throw`, and must not
  `longjmp`; `trap()` detects the misuse at runtime (`wasmCallDepth() != 0`)
  and aborts with a diagnostic rather than unwinding a generated frame;
- a **native import** is the one place where a throw is allowed, because
  `WasmBase/WasmNativeImport.hpp`'s `nativeImport<&fn>()` trampoline catches it
  and converts it into a pending trap before it reaches generated code
  ([`ABI.md`](ABI.md) "Writing an import"); an unwrapped import gets the abort
  above;
- it may hold any C++ object across the failure point — the early return runs its
  destructor, which is exactly why the POD-only rule is gone;
- the backend must emit a pending check after the call (`emitPendingTrapCheck`),
  so a forgotten check cannot silently swallow the trap.

`ModuleInstance::refDrop` (a *host* API, not a helper) reports through the
internal path and then calls `checkTrap()`: at the host boundary that throws, and
inside generated code it is a no-op because the slot is left pending for the
caller's check.

The cross-thread and lock-ownership consequences are in
[`THREADSAFETY.md`](THREADSAFETY.md) §5.6 and §10.1. The design that replaced the
old `longjmp`/`TrapScope` model, including the reasons each alternative was
rejected, is [`TRAP_CLEANUP.md`](TRAP_CLEANUP.md); the backend feasibility study
is its §10, and the shipped subset is TRAP-1/TRAP-3 there.

### 2.7 Execution state is per agent, not per host thread

`WASM::ExecutionState` — owned by an `Agent` — holds the tail-call state, the
trap slot, the pending exception, the deferred-cleanup stack, the call/import
depth counters and the stack limit. A host thread only holds a pointer to the
*current* state; generated code reaches it through `currentTailCallState()`,
`wasm_trap_slot()` and `wasm_exn_slot()`, so the state moves with the agent (or a
future continuation context), not with the thread. A host thread that has not
installed an explicit agent gets a lazily created default one. The `Store`
remains a process-global owner with locked management containers, and one
`ModuleInstance` is still not concurrently callable. These are host-side
properties, not a multi-agent execution model. A continuation installs its own
`ExecutionState` for the duration of its execution: A switches to it on a
private native stack on the same host thread, B runs it on a worker thread. The
state is private to the continuation, which is **not** an agent and does not
enter the instance while the resumer is waiting. The distinction between
guest, host and boundary safety, and the responsibilities of each party, is
defined in [`THREADSAFETY.md`](THREADSAFETY.md); the single-agent execution
model is [`proposals/THREADS.md`](proposals/THREADS.md) §3/TD9. Per-agent trap,
exception and tail-call state (**TRAP-6**) is implemented; true multi-agent
execution remains deferred indefinitely ([`TRAP_CLEANUP.md`](TRAP_CLEANUP.md)
§12.1, [`proposals/THREADS.md`](proposals/THREADS.md) TH-5).

### 2.8 The host stack is a bounded resource, and its limit is a trap

Wasm recursion runs on the host stack, so unbounded recursion is a host resource
failure exactly like an unbounded `memory.grow`. The kernel's guard page does
**not** turn it into a Wasm trap: it delivers `SIGSEGV` — the
`segfault at <rsp> ... error 6` line in `dmesg` — and takes the embedding process
down. The engine therefore checks explicitly:

- `VMContext::stackLimit` holds the lowest address generated code may let its
  frame reach on the executing host thread. The core installs it from the
  thread's real stack bounds, keeping `kDefaultStackReserveBytes` (512 KiB) back
  from the guard page (`WasmBase/WasmStack.hpp`, `installStackLimit`), on the
  thread that creates the instance (§2.7).
- The limit that governs a call belongs to the **execution state**
  (`ExecutionState::stackLimit`), not to the instance: the host boundary
  (`CallDepthScope`) installs the *calling* thread's limit on the outermost entry
  if that state has not run on this thread before
  (`ensureCurrentThreadStackLimit`). An instance created on one host thread can
  therefore be called from another without tripping the creating thread's
  guard; `VMContext::stackLimit` remains the compatibility fallback for a
  caller that bypasses the boundary.
- `PreparedFunctionStack::prepare` refuses a function whose parameters and
  declared locals would need more than `kMaxFunctionLocalBytes` (64 KiB) of
  stack storage. This is not cosmetic: a backend allocates the frame in its
  prologue and the guard check runs only afterwards, so a frame larger than the
  reserve could jump over the guard page before the check could trap.
- Generated code calls `wasm_stack_check(VMContext*)` on every compiled-function
  entry; the helper reports `TrapKind::CallStackExhausted` ("call stack
  exhausted"), an ordinary recoverable trap (§2.4) that unwinds by returning and
  becomes `WASM::Trap` at the host boundary.
- A continuation installs the same guard for its own stack
  (`WasmContinuation.cpp`): A places a `PROT_NONE` page below its mmap'd stack
  and sets a 64 KiB reserve; B does the equivalent for its pthread stack. If the
  platform cannot report B's bounds, B disarms the `VMContext` fallback rather
  than compare two unrelated mappings. Each stack is charged to the allocation
  budget and can be set with `WASMJIT_CONT_STACK_BYTES`.
- A calls the weak `__sanitizer_start_switch_fiber` /
  `__sanitizer_finish_switch_fiber` hooks around every `swapcontext` when the
  sanitizer is linked; a normal build links no libasan and the hooks are no-ops.
- For the instance-owning thread, a platform that cannot report stack bounds, or
  a thread whose stack is not larger than twice the reserve, leaves the limit at
  zero: the guard is then disarmed rather than trapping on the first call. The
  embedder chooses thread stack sizes, so this is a deliberate limitation (S7).

*Encountered pitfall:* the spec harness used to run `assert_exhaustion` in a
nested child and count that child's `SIGSEGV` as a pass. A full sweep produced
hundreds of `dmesg` segfaults and a core dump per assertion, and a module that
recursed outside `assert_exhaustion` killed the real process. The regression test
is `Test/wasm_wat/stack_exhaustion.wat` plus the
"unbounded Wasm recursion traps with 'call stack exhausted'" case in
`Test/main.cpp`.

## 3. Known limitations and false alarms

### 3.1 Deliberate limitations

| # | Limitation | Why / mitigation |
|---|---|---|
| S1 | **No instruction/step budget.** A trap-free `loop` runs forever. | Out of scope; the harness kills the child after a wall-clock timeout, and an embedder running hostile code should do the same. |
| S2 | **Negative-module coverage is opt-in, and the validator is conservative.** `assert_invalid` / `assert_unlinkable` / `assert_uninstantiable` are skipped in the default run and only executed with `WASM_SPEC_VALIDATE=1`; an opcode with no rule taints the rest of its body rather than being rejected, and text-format modules are not decoded at all (946 commands). | `Module::validate()` covers all 2,382 binary negative commands ([`VALIDATION.md`](VALIDATION.md)); the remaining holes are coverage, not acceptance. It is why §2.2 is about *resource safety*, not spec conformance. |
| S3 | **GC reclamation is not a leak-free guarantee.** Reference counting + cycle collection reclaim acyclic and cyclic garbage at safepoints, but an uncounted borrow, a wrong count or a type outside the instance can leak until instance teardown; ordinary recycled blocks also do not refund their region's budget charge. | RC-1/1b/2/3 and the reclamation tests ([`proposals/GC.md`](proposals/GC.md) §6/§7); `GcHeap::releaseSet` at teardown is the backstop, and the allocation budget still bounds total host memory. |
| S4 | **Budgets are per store, not per instance.** Instances sharing a store (they only can if they come from the same runtime) share one budget, so one greedy module can starve its siblings. | The budget lives in the `Store`, and `ES-2` made stores runtime-scoped: two runtimes are isolated. Per-instance accounting remains a possible refinement. |
| S5 | **Trap messages are not compared.** The harness checks *that* a trap happened, not its text. | Text differs between engines; the spec's strings are hints. |
| S6 | **An opt-out can unguard everything**: `WASMJIT_MAX_TOTAL_BYTES=unlimited`, or a device that reports no size (`requireAvailable` then cannot bound). | Both are explicit choices. |
| S7 | **A thread whose stack is not larger than twice the guard reserve runs unguarded** (`stackLimit == 0`), as does a platform that cannot report stack bounds. | A 64 KiB frame cannot be made safe on an arbitrarily small stack; the embedder owns thread stack sizes. §2.8. |
| S8 | **A continuation use is serial.** A suspended stack may migrate between host threads, but concurrent resume/drop of the same continuation is undefined; B cancels on its worker. | Keep one host thread active per continuation at a time; the provider does not add a scheduler. |

### 3.2 Things that looked like engine bugs but were not

- **"A reference-argument spec case failed"** — before the harness learned to
  marshal reference and `v128` values (`Test/WastScript.cpp`: `referenceArgument`
  / `decodeV128`), such an action was *skipped* and a following assertion about
  the resulting state legitimately failed (e.g. `table_grow`'s two failures).
  Both are marshalled now and those cases pass; the only remaining harness skips
  are text-format modules and the `module_instance` linking command.
- **A "no report" child** — the per-script child died before writing its report;
  `WJ_TRACE=1` prints each command to stderr, so the last line names the culprit
  ([`TESTING.md`](TESTING.md)). The full sweep currently produces none.

### 3.3 What multi-agent execution adds to the threat model (design direction)

Multi-agent execution is the accepted design direction
([`MULTI_AGENT_FEASIBILITY.md`](MULTI_AGENT_FEASIBILITY.md) §2.3), and it changes
the security arithmetic even though it is not implemented yet: N agents mean N
concurrent trails through one instance, one GC heap entry point and one allocation
budget. None of the rows below is a new *policy*; each is an existing limitation
that gets sharper.

| # | Concern | Why N agents make it worse | Mitigation / owner |
|---|---|---|---|
| A1 | **No instruction/step budget** (`S1`) | One runaway agent becomes N; a game that trusted one call's latency now has N stalls | Embedder-owned wall-clock/watchdog (unchanged policy; the runtime should expose a per-agent park point so a watchdog can actually stop one) |
| A2 | **Process-wide allocation budget** (`S4`) | One agent's GC pressure starves the others, and the failure is a trap in an unrelated agent | Per-runtime budgets once `WASM::Runtime` owns the `Store` ([`EMBEDDING_SURFACE.md`](EMBEDDING_SURFACE.md) §4.3) |
| A3 | **GC reclamation is embedder-driven** (`S3`) | If nobody calls `gcCollect()` at a safepoint, the queue grows forever and the budget closes the world | The runtime must call the safepoint per frame; with agents, a documented quiescence rule (`MULTI_AGENT_FEASIBILITY.md` §2.3.5) |
| A4 | **Per-agent stack limits** (`S7`) | Each agent needs its own guarded stack; a small thread stack still runs unguarded | Already per `ExecutionState`; continuation stacks install their own limit |
| A5 | **A blocking `wait` is degenerate today** (`S8` analogue) | A guest can park an agent forever, or spin if the waiter table lies | The waiter table plus join/cancel (`THREADS.md` MA-4, `MF-5`) |
| A6 | **Host imports must be reentrant** | A non-reentrant import reached by two agents is a use-after-free, not a slowdown | `THREADSAFETY.md` §9 item 5; the engine cannot add an import lock without changing the contract |
| A7 | **`hostData` is host-synchronized** | Two agents reach the same `hostData` concurrently | Embedder responsibility, documented in `THREADSAFETY.md` §5/§9 |
| A8 | **No isolation by instance** | Multiple instances are ruled out by design, so a hostile module affects every agent on its instance | The isolation boundary is the *runtime* (separate `Store`, separate budget), not a second instance |

The rule that makes this tractable: **the engine hardens the instance; the
embedder hardens its threads, imports and frame loop.** Any hardening the engine
adds must be visible in this table before agents can be enabled by default.

## 4. Case studies (pitfalls actually encountered)

**1. The `grow` OOM (host freeze).** A MEMORY64 change made the grow delta
unsigned without adding the spec's size caps, so `(table.grow … 0xffffffff)`
became a ~34 GB `resize`. Fix: the Store allocation budget plus index-space caps
(§2.3), and the regression test `Test/wasm_wat/grow_guard.wat`
(`grow guardrail rejects absurd deltas without allocating`), which asserts `-1`
*and* that nothing was charged. Verified by running the whole suite under a
64 MiB budget and a `ulimit -v 4 GiB`.

**2. The LibJIT context lock (hang).** Making `notImplemented` throw — to turn a
host-killing abort into a clean failure — made the *next* module in the same
script hang. Cause: the throw unwound out of the `jit_context_build_start` …
`build_end` region, so the lock was never released. Fix: `JitBuildScope` (§2.5).
Verified: `simd_const` now reports 121 passed / 360 failed instead of hanging or
killing the process, and the full sweep lost all 8 "produced no report" children.

**3. Traps that did not trap.** `i32.div_s` by zero, the trapping `trunc_f*`
forms and the `memory.init` bounds checks were lowered with bare LibJIT `div` /
`convert`, or with `std::abort()`, so once `assert_trap` started to run they
either passed silently or killed the process. Fix: the trap sink plus native
helpers that check (`proposals/SMALL_PROPOSALS.md` rev 3,
[`proposals/BULK_MEMORY.md`](proposals/BULK_MEMORY.md) BM-2). This also fixed the
GC / function-reference crashes (`call_ref`, `ref_func`, `type-equivalence`,
`array_init_*`).

**4. A 5-byte LEB asking for 4 GiB.** `readLEB128String`, `body.code.resize`,
`seg.data.resize`, `readList` and the local counts all took their size straight
from the input. Fix: §2.2. `PreparedFunctionStack::prepare` also truncated its
`localCount` to `uint16_t`; the counts are now `uint32_t`.

## 5. Checklist for a new feature

1. Does it read a **size or count** from the module? Bound it (§2.2) — by the
   remaining input, or by a named cap in `WasmSafety.hpp`.
2. Does it **allocate host memory** (memory, table, GC object, arena)? Charge it
   against the `Store` budget and fail as `-1` / trap (§2.3). On the
   generated-code path, allocate from the mmap-backed `GcHeap`, not
   `malloc`/`calloc`.
3. Does it **fail at runtime**? On a path generated code calls directly, use
   `WASM::reportTrap` and return a benign value — never `abort`, never an
   escaping exception (§2.4, §2.6); at the host boundary, `WASM::trap` throws.
   Any C++ locals may be live, so RAII is fine.
4. Does it **fail at load / instantiate / compile time**? Throw an exception with
   a message that says what was wrong — and if you are inside a begin/end region,
   make it RAII first (§2.5).
5. Does it introduce **execution state**? Put it in `ExecutionState`
   (`WasmAgent.hpp`) behind the current-agent accessors, not in a new
   `thread_local`; reset it when the trap is reported, and document the
   single-agent assumption (§2.6, §2.7).
6. Does it **recurse on the host stack** because of module input? Rely on the
   guest stack guard, and keep one frame well below its reserve (§2.8).
7. Add a **regression test** that would have caught the failure: a `*.wat` plus a
   `TEST_CASE`, or a budget-bounded run of the suite.

## 6. How to verify the guardrails

```bash
cd build/Desktop-Debug/Test

# The whole default suite must stay green...
./WasmJit

# ...and must also fit in a tiny budget (proves nothing allocates wildly).
WASMJIT_MAX_TOTAL_BYTES=67108864 ./WasmJit

# The dedicated regression test for the grow guardrail.
./WasmJit "grow guardrail rejects absurd deltas without allocating"

# The dedicated regression test for the host stack guard: unbounded Wasm
# recursion must trap, and must not add a `segfault` line to dmesg (§2.8).
dmesg | grep -c 'WasmJit.*segfault'      # note the count first
./WasmJit "unbounded Wasm recursion traps with 'call stack exhausted'"
dmesg | grep -c 'WasmJit.*segfault'      # must be unchanged

# Belt and braces: cap the address space as well, so a regression cannot touch
# the machine even if the budget is bypassed.
bash -c 'ulimit -v 4194304; WASMJIT_MAX_TOTAL_BYTES=8388608 ./WasmJit "grow guardrail rejects absurd deltas without allocating"'

# A full survey (tolerant): read the per-script lines and look for
# "terminated by signal" / "produced no report" — both should be rare, and are
# never acceptable on the *curated* set.
WASM_SPEC_TOLERANT=1 WASM_SPEC_TIMEOUT=8 WASM_SPEC_SCRIPTS=all ./WasmJit -r compact | tee sweep.log
grep -c 'terminated by signal\|produced no report' sweep.log
```

`WJ_TRACE=1` prints every command before it runs — the way to find which command
killed a child that "produced no report".
